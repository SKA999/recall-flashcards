Recall

A spaced-repetition flashcard app built from scratch around FSRS-5, with the scheduling core kept free of platform dependencies so a native app can reuse it.

Live ska999.github.io/recall-flashcards Repo SKA999/recall-flashcards

Where things stand

Six commits, deployed from main by GitHub Actions on every push, with the test suite gating the deploy.

Shipped FSRS-5 scheduling

The real algorithm — forgetting curve, stability and difficulty updates, lapse handling, same-day formula, Anki's interval fuzz. Learning steps sit in front of it, with a 4am day rollover.

Shipped Notes, note types, cloze

Notes carry named fields; a note type says which fields each card asks and answers. Cloze generates one card per deletion. Editing a note never disturbs the scheduling of cards that survive.

Shipped Review and undo

True interval previews on each button, keyboard control, daily limits, study-ahead. Undo goes 30 answers deep and restores the card, the log and the day's counters.

Shipped Media

Images, audio and video on any field, stored as blobs. Card text renders as text, never HTML, so imported content cannot inject markup.

Shipped Statistics

Reviews per day, grade breakdown, 30-day forecast, card maturity. Palette validated for colour-vision separation and surface contrast in both themes.

Shipped CSV import

RFC 4180 parsing, delimiter detection by column consistency, and Anki's own text-export preamble. Two sample files ship in examples/, covered by tests.

Shipped Backup

The whole collection to one inspectable zip, and back. Restore merges by id and never overwrites, so an old backup cannot undo newer reviews.

Shipped Offline, installable

Service worker verified active on the live site. Installable to a phone home screen as a PWA.

Half built Anki .apkg import

All the parsing is done and tested: zip reader with zip64, zstd, the package protobufs, both collection schemas, note-type mapping, media conversion. What remains is writing it into the collection, and the screen to drive it.

Not started Sync

The local half exists — every record carries an updated stamp and deletes write tombstones. The backend, accounts and conflict policy do not.

Not started Native phone app

The PWA installs today. A native app would reuse src/core unchanged and supply a SQLite store.

What to be wary of

Unverified against reality

Every Anki-format claim is verified against packages generated from Anki's published schema and protobuf definitions — never against a real export. That is genuinely good coverage of the format, but it cannot catch a note-type shape or media convention that only exists in a real collection. A single exported deck would settle it.

One device, one collection

Without sync, a collection lives in one browser on one machine. Backup is currently the only way to move it, and the only protection against clearing browser data. Restore merges and never overwrites — there is no replace mode yet, which is deliberate but means a newer backup cannot correct older records.

Next steps

Ordered by dependency rather than preference — step 3 genuinely cannot come before step 2.

  1. Finish .apkg import

    Orchestration and the import screen; the hard parsing is behind us. About a day. Worth doing whenever Anki decks are actually in play, and worth deferring if they never are.

    Needs: nothing. Blocks: nothing.

  2. Sync

    A backend, accounts, and a conflict policy. The largest single piece here, and the one that turns this from an app on one machine into an app you keep.

    Needs: a hosting decision. Blocks: the phone app.

  3. Native phone app

    Reuses the scheduling core as-is and swaps IndexedDB for SQLite. Building it before sync produces two collections that disagree, which for spaced repetition is worse than one.

    Needs: sync.

Smaller things, any time

A replace mode for restore, behind a confirmation. Deck rename and bulk operations from the browse list. Per-user FSRS weight optimisation — the review log already records everything it would need.
